# A trip's description & daily spend

- **Daily food & drink** (`daily_spend_service.go`, `daily_spend_handler.go`, migration 00070; specs/daily-spend-guide): the Budget tab suggests a per-person daily food estimate per city and files an accepted one as a **planned** expense — the first thing giving 00067's planned-vs-paid comparison something to compare against. The figure is a **labelled model estimate and says so on every render**, because the alternatives were checked and are not available: no free global currency-denominated meal-price feed exists, and this API is on the LEGACY Places API whose `price_level` is an ordinal 0-4 (`hotel_search_service.go:285` already refused to map that onto money). `DailySpendGuide.Basis` carries `"estimate"` on the wire the way `WeatherReport.Kind` carries forecast-vs-historical, so a real provider later is a NEW basis value, not a silent change of meaning. `resolveSpendTier` is the explicit ladder (`?tier=` → `traveler_preferences.budget` → **`mid`**), modelled on `resolveBaggageTier`, and the response echoes the RESOLVED tier **plus its source** so the card can credit a saved preference truthfully instead of implying one. An unrecognized REQUESTED tier is refused; an unrecognized STORED one falls through (data, not a claim). **The multiplier is NIGHTS, not days**: two legs share their transition day, so days would bill it twice and the section could never reconcile with the trip's own length — nights come from `computeTripLegs` + `nightsBetween`, the same derivation as the city header chip, pinned by `TestDailySpendNightsMatchRenderedLegs`. The server sends the per-person rate and the nights but **never a total**: party size is the one thing it cannot know, so `dailySpendTotal` (`utils/daily_spend.dart`) is the one multiplication and both the figure on the card and the amount the button posts read it. Travelers count is session-local and starts at 1, deliberately NOT inferred from `traveler_preferences.companions` — that is a taste, not a headcount. **`trip_expenses.leg_key` (00070) is what makes "already in the plan" answerable**: without an identity the card cannot tell, and a second tap duplicates the line; matching the generated label would make the LABEL the key, the failure 00064 was written to undo. It is a snapshot (no FK, 00061's pattern), it is NOT part of the `auto` contract (a city plan is the traveler's, so no booking-state change may reach it), the POST is its one writer and **PATCH has no mechanism to move a line to another city** (pinned by `TestPatchExpenseCannotSetLegKey`), and `tripLegKeyExists` canonicalizes it server-side against `computeTripLegs` so a stale tab cannot mint an orphan. Everything degrades to "no section": no API key, a provider failure, a trip with no dated cities, a viewer, or offline — all 200 with a stable reason code. A city the model omits or prices implausibly is **dropped, never given a neighbour's number**. Cache is 30 days (city food costs move by season) and is the endpoint's only real spend guard.

- **A trip's description** (`trip_summary.go`, `plan_trip_description.go`, migration 00071; specs/trip-description): `trips.summary` (00013) is the prose overview under a trip's title, and it was **write-once at `CreateTrip`** until now — `UpdateTrip` omits it from its COALESCE set, `create_itinerary` supplies it and is then gated OFF for a bound trip, and `get_trip` never rendered it, so a blurb describing three cities outlived the trip growing to five with nobody able to fix it. **`applyTripSummary` is the ONE writer**, called by `PATCH /trips/{id}`'s new `summary` key and by the agent's `set_trip_description` (registry TAIL, `authedOnly`) — pinned by `TestPageAndChatWriteTheSameDescription`. It goes through a dedicated `SetTripSummary` (plain `narg`, **no COALESCE**) rather than `UpdateTrip` because COALESCE cannot carry "write NULL", so a description could be set and replaced but never CLEARED; `""` normalizes to NULL so "no description" keeps exactly one representation. **`summary_source` ('agent'|'traveler', 00071) makes authorship storage, not a prompt rule**: the planner may refresh prose it wrote and is refused by the SERVER against prose the traveler wrote — hence the tool's required `reason` (`traveler_asked` always writes; `trip_changed` refuses on `'traveler'`, quoting what is there so it can offer instead). The PAIR carries a meaning neither column holds: `summary IS NULL` + `'traveler'` is a deliberate REMOVAL, which is why clearing stamps `'traveler'` and not NULL; a NULL source is provably not the traveler's (no human writer existed pre-00071) and stays refreshable. `persistTrip` stamps `'agent'` and **carries the previous version's prose AND author forward** when a version save supplies none — every save INSERTs, so without it a re-save dropped the description with no UPDATE statement existing anywhere. The model can finally SEE it: `tripDescriptionSummary` rides `get_trip` and `update_itinerary_section`'s echo (the `legTransportSummary` trick — a stale description becomes something visible rather than something to remember), and it is explicit about BOTH ways of being absent. Naming diverges on purpose: storage/wire/`create_itinerary` stay `summary`, the tool and the UI say "description", because the compaction state already reaches the model as a message opening "Summary of the conversation so far". Client-side one dialog edits the name and the description together (`trip_details_dialog.dart`, the header pencil), seeded from `_displayTitle`/`_overviewText` so a legacy trip whose prose lives in `title` promotes it into `summary` on first save. `trips.summary` was also removed from `TestSharedWithMeInsightAbsence`'s withheld list: it is not owner planning state — `GET /trips/{id}` hands it to editors and viewers unredacted and the public share page renders it — so its absence only meant a co-planner's cards showed no blurb.
