# What a Flutter widget test can and cannot prove

- **A widget test cannot see a font, so it cannot answer a layout question.** `src/packages/flutter-app/test/` has **no `flutter_test_config.dart` and loads no font assets**, so every widget test lays out in Flutter's built-in test font — a fixed-width stand-in, *wider* than Inter at the same size. Every width, height, line count, wrap point, fold position, ellipsis and overflow in a widget test is therefore a fact about that stand-in, and none of them transfers to the shipped app. This has produced three separate false conclusions in one feature (the travel atlas): a "both header actions share one line" test that pinned a three-line stack the app never renders, a pair of position assertions that only described the test font, and a chip tap at a fixed offset that landed off-screen and made its test pass vacuously. PR #511 exists mostly to undo them. **So: never write, and never restore, an assertion that depends on rendered text size.** What a widget test CAN hold is everything font-independent — which widget is inside which, presence and absence, a state or callback, a color or other resolved property, a constant the code sets outright (`SizedBox(height: kAtlasPlateHeight)`), and a runtime fact the framework itself reports. A claim about the fold, the wrap, or what fits is **verified in the browser at real widths in both languages** and then written down as a comment saying so and saying the assertion is deliberately absent — a test modelling the wrong fold is worse than no test, because it fails on correct code and passes on broken. Two consequences worth knowing: rigid chrome elsewhere on a page can overflow in the test font and not in the app (consume it with `takeException`, and assert it is the ONLY one, so a real second overflow still fails), and a `tap()` positioned by preceding text needs `scrollUntilVisible` — a bare `tap()` on an off-screen widget only WARNS, it does not fail.
